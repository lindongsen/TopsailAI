# Environment Variables

> Description Rule: Keep every variable description concise. State only the purpose, default behavior, and valid values; avoid redundant explanations or examples unless essential for clarity.

This document provides a reference for environment variables used by TopsailAI.

## Workspace and Project Folders

These variables define the agent's working environment and project access scope.

| Variable | Default | Description |
|----------|---------|-------------|
| `TOPSAILAI_HOME` | `""` | Agent workspace folder. Holds files generated by the agent process, including `log`, `lock`, `task`, and `story_memory`. Defines the agent's working environment. |
| `TOPSAILAI_WORK_FOLDER` | (runtime) | Working directory of the agent process, holding `.env`, `db`, etc. Set automatically when the process starts; cannot be set manually. |
| `TOPSAILAI_PROJECT_WORKSPACE` | `""` | Alias `TOPSAILAI_PROJECT_FOLDER`. The project folder is the permission range the agent may actively read and write. |
| `TOPSAILAI_PWD` | `""` | Print Working Directory, i.e. the folder at the time of process startup. |
| `TOPSAILAI_PROJECT_WORKSPACE_LOCK_ENABLED` | `1` | When `1`, a project workspace lock is acquired at startup. Set to `0` to disable project workspace locking. |
| `TOPSAILAI_PROJECT_WORKSPACE_LOCK_TIMEOUT` | `300` | Timeout in seconds for the interactive prompt when the project workspace lock cannot be acquired. The user can choose `exit`, `continue`, or `wait`. If the timeout expires or no input is received, the default action is `wait`. |

### Threshold Resolution

Each layer first reads its own message-count threshold. If that value is unset, empty, `0`, or negative, the layer falls back to `TOPSAILAI_CONTEXT_MESSAGES_QUANTITY_THRESHOLD`. If the shared threshold is also unset, empty, `0`, or negative, quantity-based summarization is disabled for that layer.

Token-based checks run in addition to the message-count check and are disabled by setting their threshold to `0`. The duplicate tool-call check runs in addition to both and is disabled by setting its threshold to `0` or negative.

## Database Write I/O Failure

These variables control how a database **write** reacts to an I/O failure. Reads are out of scope and keep failing fast.

| Variable | Default | Description |
|----------|---------|-------------|
| `TOPSAILAI_DB_WRITE_MAX_BLOCK_SECONDS` | `0` | Maximum number of seconds one database write may block while waiting for a competing writer or a pooled connection. `0`, negative, empty, or invalid values block indefinitely. A positive value bounds the wait; when the budget is exhausted the process exits with code `1`. |

### Behavior

- **Scope is writes only.** Reads keep the driver default, so a stuck write can never make a read hang.
- **Transient failures block.** Lock contention and an exhausted connection pool wait instead of failing fast. The widened wait applies only to the write connection and is restored afterwards, so it never leaks onto a later read.
- **Unrecoverable failures exit immediately.** Read-only, I/O error, corrupt, disk-full, cannot-open, protocol, and not-a-database conditions never resolve by waiting, so the process exits at once instead of turning a recoverable failure into a permanently hung agent.
- **Exit is process-wide.** Log handlers and standard streams are flushed before the process terminates, so a background thread cannot leave the process half-alive.
- **A business result is not an I/O failure.** A missing session is a normal result, and a non-I/O exception keeps its original contract, so a programming defect stays testable instead of terminating the process.
- **Callers never downgrade an I/O failure.** A failed write is re-raised instead of being logged as a warning, so a lost write cannot look like success.

## Agent2LLM Summary Session-Message Tuning

These variables tune the conditions under which the agent-layer summarizer keeps or drops session messages when `TOPSAILAI_CTX_SUMMARY_KEEP_SESSION_MESSAGES` is enabled.

| Variable | Default | Description |
|----------|---------|-------------|
| `TOPSAILAI_AGENT2LLM_SUMMARY_SESSION_MAX_RATIO` | `0.5` | Maximum ratio of the agent-layer quantity threshold that the session may occupy before session messages are dropped from the summary. Must be a float in `(0, 1]`. Values outside this range fall back to `0.5`. |
| `TOPSAILAI_AGENT2LLM_SUMMARY_MIN_EXTRA_MESSAGES` | `17` | Minimum number of extra agent-layer messages required beyond the session length for the summary to be considered worthwhile. Must be a non-negative integer. Negative values fall back to `17`. |

### Behavior

- With the default `0.5` and an effective agent-layer quantity threshold of `97`, session messages are dropped once the session reaches `48` messages.
- If the total agent-layer message count is less than the session length plus the minimum extra messages, summarization is skipped because the context is not long enough to justify a summary.

## Agent2LLM Message Persistence

`TOPSAILAI_AGENT2LLM_KEEP_MESSAGES_ACROSS_TURNS` controls whether the agent-layer message context is reset at the start of each user turn.

- When `0` (default), the agent context is reset to the system prompts at the start of each turn and then filled with the full current session messages, so each turn starts from a clean context containing only the persisted session history.
- When `1`, the existing agent messages are preserved and only the environment message is refreshed. Session messages not already present are appended, so the agent context accumulates across turns and keeps previous reasoning, tool calls, and observations.

Enabling persistence makes the agent context grow faster, so the agent-layer quantity and token thresholds may need to be lowered to trigger summarization sooner.

## Repeated Tool-Call Warning

| Variable | Default | Description |
|----------|---------|-------------|
| `TOPSAILAI_TOOL_CALL_WARNING_RULES` | `""` | JSON list of dicts defining repeated tool-call warning rules. Empty or unset disables the feature. Each rule keys: `agent_role` (default `*`), `tool_call` (required, exact tool name or `*`), `max_calls` (required, positive integer), `window_seconds` (default `60`), `warning` (required template), `enabled` (default `true`), `dedup` (default `true`). `window_seconds`: positive counts within a rolling time window; non-positive counts only strictly consecutive calls to the same tool. Placeholders in `warning`: `{tool_call}`, `{count}`, `{agent_role}`, `{window_seconds}`, `{max_calls}`, `{member_suggestion}`. `{member_suggestion}` renders a delegation hint for manager-role rules and is empty for other roles. Matching: first matching rule wins (role match or `*` AND tool match or `*`). Advisory only: configuration errors never interrupt tool execution. |

### Behavior

- **Semantics**: A warning is emitted when the number of calls to a matching tool within the rolling window exceeds `max_calls`. The triggering call is included in the count.
- **Matching and precedence**: Rules are evaluated in declared order; the first rule whose role and tool both match wins.
- **Validation and fallback**: Invalid JSON or non-list JSON disables the feature with a warning. Invalid individual rules are skipped with a warning. Unknown roles are treated as `*`. Invalid `window_seconds` falls back to `60`. A missing or empty `warning` skips the rule.
- **Dedup**: With `dedup=true` (default), a rule warns only once while the count stays above `max_calls` and re-arms after the count falls back to or below `max_calls`.
- **Injection**: On trigger, the warning is injected into the agent context as a user-role observation before the next LLM call. The original tool result is never altered.

## Tool Approval

These variables configure the optional tool-call approval gate. When enabled, each tool invocation is evaluated against a set of rules; matching rules can require explicit human approval before the tool runs.

| Variable | Default | Description |
|----------|---------|-------------|
| `TOPSAILAI_TOOL_APPROVAL_ENABLED` | `0` | Master switch. `1` enables the approval mechanism, `0` disables it. |
| `TOPSAILAI_TOOL_APPROVAL_RULES` | `${TOPSAILAI_WORK_FOLDER}/tool_approval.json` | JSON approval rules. Either a JSON array literal or one or more paths to files containing a JSON array, separated by `;`. Rules from all files are aggregated in order. |
| `TOPSAILAI_TOOL_APPROVAL_DEFAULT_TIMEOUT` | `60` | Default timeout in seconds when a rule does not specify one. |
| `TOPSAILAI_TOOL_APPROVAL_DEFAULT_POLICY` | `deny` | Default timeout policy when a rule does not specify one. Must be one of `deny`, `allow`, `ask_again`. |
| `TOPSAILAI_TOOL_APPROVAL_DISPLAY_MAX_LINES` | `40` | Maximum rendered lines for one multi-line argument value in the approval request prompt. Longer values are truncated with a `(+N lines)` marker. Positive integer; invalid or non-positive values fall back to `40`. |
| `TOPSAILAI_TOOL_APPROVAL_DISPLAY_MAX_VALUE_CHARS` | `2000` | Maximum rendered characters for one scalar argument value in the approval request prompt. Longer values are truncated with a `(+N chars)` marker. Positive integer; invalid or non-positive values fall back to `2000`. |

### Behavior

- `TOPSAILAI_TOOL_APPROVAL_RULES` is read at call time, so rules can be updated without restarting the agent. Multiple files are parsed and their rule arrays concatenated in the order given.
- If the variable is empty or unset, the default path is used. If that file does not exist, approval is effectively disabled and all tool calls execute normally.
- On a JSON parsing failure or unreadable path, the offending file is skipped and the remaining files are still evaluated. If all configured files fail, approval is disabled for the current process and tool calls execute normally.
- Rule `mode` values: `require` (approval needed), `bypass` (skip approval), `skip` (alias for `bypass`). Unknown modes are treated as `require`.
- Rule `policy` values: `deny` (reject on timeout), `allow` (auto-approve on timeout), `ask_again` (reset and wait one extra cycle, then deny). Unknown policies are treated as `deny`.
- The approval prompt renders arguments in an indented multi-line form: strings containing line breaks are printed literally behind a `| ` marker, containers are printed one entry per line, and an empty argument mapping renders as `(none)`.
- The prompt shows a minimal focus block below the request id with exactly two lines: the matched rule name and its tool-name pattern. Parameter conditions are not rendered because the full arguments are already displayed. When no rule matched, the block is omitted.
- The display limits only bound the displayed text; the tool always receives the original untruncated arguments.

| Variable | Default | Description |

### Hook Point Behavior

- `{}` is not disablement: built-in point-local resources are still discovered and merged with configured external resources.
- Modules run before executable scripts, each in filename order.
- Scripts run directly without arguments or payload, manifest, interpreter allowlist, or dependency admission.
- This prototype is POSIX-only and independent of the configured-Hook variables below; it does not remove their trust rules.
- Its five-second aggregate execution budget is not a strict total-call bound: discovery and global-lock waiting are not bounded by that timer, and cleanup may add a one-second wait per child.
- Plugin output and return values are discarded, and ordinary failures are reported without changing the input.
- Unresolved cleanup records block new plugin starts; there is no explicit operator settlement API, and restart does not prove descendants are gone.
- Process-group cleanup is not a sandbox and does not contain deliberately escaping descendants.

## Thought/Final-Answer Abnormal Line-Ratio Detection

These variables detect LLM responses that are finally classified as `thought` or `final_answer` but whose non-empty lines contain a configurable substring beyond a ratio threshold. For a thought, a critical user observation is appended warning the model. For a final answer, the step is converted back to a thought (the task is NOT terminated) and the same critical observation is injected so the model gets another chance.

| Variable | Default | Description |
|----------|---------|-------------|
| `TOPSAILAI_THOUGHT_LINE_PATTERN_ENABLED` | `0` | Master switch. `1` enables detection, `0` disables it. When disabled, no scanning occurs and existing behavior is preserved exactly. |
| `TOPSAILAI_THOUGHT_LINE_PATTERN_RULES` | `""` | JSON list of rule dicts defining abnormal line-pattern detection. Empty or invalid disables the feature. See the rule fields below. |

### Rule Fields

Each element in `TOPSAILAI_THOUGHT_LINE_PATTERN_RULES` supports:

| Field | Required | Default | Description |
|-------|----------|---------|-------------|
| `pattern` | yes | — | Substring that a stripped non-empty line must contain. Unicode supported; matching is exact (no normalization). |
| `line_ratio` | yes | — | Trigger ratio, must satisfy `0 < value <= 1`. A rule fires when the matched ratio is STRICTLY greater than this value. |
| `min_lines` | no | `5` | Minimum number of non-empty lines required before evaluation. Below this, the rule never fires, which avoids false positives on short text. |
| `case_sensitive` | no | `true` | Whether substring matching is case-sensitive. |
| `enabled` | no | `true` | Whether the rule is active. |
| `dedup` | no | `true` | When true, warns only once per sustained over-threshold period and re-arms after the ratio falls back to or below the threshold. |
| `agent_role` | no | `*` | Restrict to role: `manager`, `worker`, or `*`. Unknown roles are treated as `*`. |
| `warning` | no | built-in template | Custom warning template with placeholders `{pattern}`, `{matched}`, `{total}`, `{actual_ratio}`, `{line_ratio}`, `{agent_role}`, `{step_type}`. |

### Behavior

- **Line definition**: Text is split into lines; each line is stripped; empty and whitespace-only lines are excluded from both numerator and denominator.
- **Threshold semantics**: The comparison is strictly greater, so a ratio equal to the threshold does not fire.
- **Multiple rules**: OR semantics — any enabled rule that fires contributes to a single merged critical observation per response.
- **Scan scope**: Only assistant thought and final steps are scanned. Injected observations are never rescanned, which prevents recursion.
- **Advisory only**: Configuration errors or evaluation failures are logged and swallowed; they never interrupt agent execution.
