# TopsailAI Connector

A remote access system for files and commands with an explicit permission
boundary. Two components and one client:

- **Server** — runs in the cloud, accepts Node connections and forwards the
  operations a Node advertises.
- **Node** — runs on a personal computer, dials out to the Server, keeps the
  link open and serves only the operations its local policy allows.
- **CLI** — a subcommand of the Server binary. It presents a `client_token` and a
  `node-id.node-token` pair to the Server, names the Node it wants, and prints the
  result.

The Node always initiates the connection. The Server never dials the Node, so a
personal computer needs no inbound port, no public address and no firewall
change.

## Three secrets, three gates

| Secret | Generated by | Configured where | Presented by | Validated by | Gates |
|---|---|---|---|---|---|
| `tunnel_token` | Server operator | Server environment | Node, in `hello` | Server | May this Node connect |
| `client_token` | Server operator | Server environment | CLI, every request | Server | May this caller use the Server |
| `node-id.node-token` | Node | Node config, copied to CLI | CLI, forwarded | Node | One operation on one scope |

Each secret is validated by exactly one party, and that party is the one that
issued it. The Server validates the two secrets it owns; the Node validates the
one it owns. Neither side trusts the other's claim about identity.

**No secret carries a permission.** A secret says "you may talk to me". The policy
file says "and you may do this". Keeping those separate is what stops a stolen
`client_token` from also being a stolen permission.

## How a request travels

```
CLI --(client_token + node-id.node-token)--> Server
Server compares client_token, checks the node-id, forwards node-token unchanged
Server --(node-token)--> Node over the open channel
Node compares node-token, resolves the scope, checks the policy, does the work
```

The Server never learns the correct `node-token`, so it cannot check it. It
forwards the value byte for byte and keeps no copy. That is the point: a
compromised Server cannot mint a `node-token` and cannot recognise one later.

The Server serves both surfaces from one listener and one TLS certificate: the
channel at `/channel` for Nodes, the CLI API at `/v1/` for operators. A deployment
that must keep the CLI API unreachable from the internet blocks `/v1/` at the
reverse proxy rather than opening a second port.

See `docs/permission-design.md` for the full contract.

## Status

Skeleton only. The package layout, the wire contract and the permission
vocabulary exist; the listener, the dialer, the handshake, the CLI and the
operation handlers are not implemented yet. The permission model is decided and
recorded in `docs/permission-design.md`; the CLI interface is decided and recorded
in `docs/API.md`; the test cases are recorded in `docs/cases/`; implementation has
not started.

## Supported platforms

Linux, macOS and Windows. The path fence is implemented with the standard library
`os.Root`, which enforces the boundary on all three, so the platform difference is
a set of path rules rather than a second fence implementation. Windows adds rules
for reserved device names, alternate data streams, trailing dots and
case-insensitive deny-list comparison; they are listed in
`docs/permission-design.md`.

## Skills

Three skills describe how to use the system from each audience's point of view.
Each one is self-contained: a reader who has never seen this repository can follow
it without opening the source.

| Skill | Audience | Answers |
|---|---|---|
| `skills/connector-client/` | The person calling a Node | The `cli` command, its flags, the three read operations, every error code |
| `skills/connector-server-operations/` | The Server operator | Deploy, configure, expose the two surfaces differently, rotate secrets, troubleshoot |
| `skills/connector-node-setup/` | The person running a Node | First-run order, the policy file, scope path rules, start, regenerate |

The Server has two skills rather than one because the two audiences are different
people with different questions. A client never needs to know how to rotate a
secret, and an operator never needs the client's flag syntax.

## Layout

```
topsailai_connector/
├── cmd/
│   ├── connector-server/   # cloud-side entry point
│   └── connector-node/     # personal-computer entry point
├── internal/
│   ├── protocol/           # wire contract shared by both sides
│   ├── security/           # permission vocabulary shared by both sides
│   ├── server/             # cloud-side implementation
│   └── node/               # personal-computer implementation
├── docs/                   # design documents
├── features/               # user-visible behaviour
├── issues/                 # pending, resolved and ignored issues
├── skills/                 # operator and user facing skills
└── tests/                  # integration, bdd and shared fixtures
```

`internal/` is deliberate: the Go compiler refuses an import from outside the
module, so the Node binary cannot accidentally carry server code and the Server
binary cannot carry node code. `internal/protocol` and `internal/security` are
the only packages both sides import, and they must stay free of IO so the two
binaries can never disagree about the contract.

## First run

The Node generates its own identity, so the order matters:

```
1. Start the Server with its two secrets set
   CONNECTOR_SERVER_TUNNEL_TOKEN=<secret> CONNECTOR_SERVER_CLIENT_TOKEN=<secret> \
   CONNECTOR_SERVER_LISTEN=:8443 \
     connector-server run

2. Start the Node once to create its identity
   connector-node id
     -> node_7f3a...9c1e.9f2b...4d7a      copy this whole pair

3. Give the Node the tunnel_token, then start it
   CONNECTOR_NODE_TUNNEL_TOKEN=<secret> \
   CONNECTOR_NODE_SERVER_URL=wss://host/channel \
     connector-node run

4. Point the CLI at the Node
   CONNECTOR_CLI_CLIENT_TOKEN=<secret> \
   CONNECTOR_CLI_NODE=node_7f3a...9c1e.9f2b...4d7a \
     connector-server cli --server https://host --scope project --path a.txt file.read
```

The Node must run once before anyone can address it, because the Server never
assigns an identifier. The `node-id` half is an address, not a credential:
knowing it grants nothing without the `node-token` half and a `client_token`.

The Node can regenerate its pair at any time with `connector-node regenerate`.
The old `node-token` stops working immediately and the live channel drops, so the
operator must copy the new pair to the CLI before the next request.

## Build

```
make build
```

Binaries are written to `bin/`. Test artifacts are written to `.tmp/`, which is
ignored by git.

## Package a Node for someone else

`make package` produces a zip that a user unzips and starts. The bundle carries
the Node binary, a start script for the target platform, the scope list and a
pre-generated identity pair, so the operator can reach the machine with the CLI
as soon as the user runs the start script.

```
make package PACKAGE_SERVER_URL=wss://cloud.example.com:8443/channel \
             PACKAGE_SCOPES='project=/home/me/project tool=/opt/tool'
```

The command prints the `node-id.node-token` pair and a CLI invocation to paste.
`make package-windows` builds the same bundle for Windows. See
`packaging/bundle-README.md` for what the recipient does with it.
