# TopsailAI Connector

A remote access system for files and commands with an explicit permission
boundary. Two components and one client:

- **Server** — runs in the cloud, accepts Node connections and forwards the
  operations a Node advertises.
- **Node** — runs on a personal computer, dials out to the Server, keeps the
  link open and serves only the operations its local policy allows.
- **CLI** — a subcommand of the Server binary. It signs a request with a client
  credential and a node credential, names the Node it wants, and prints the
  result.

The Node always initiates the connection. The Server never dials the Node, so a
personal computer needs no inbound port, no public address and no firewall
change.

## Three credentials, three gates

| Credential | Generated by | Configured where | Presented by | Validated by | Gates |
|---|---|---|---|---|---|
| `tunnel_token` | Server operator | Server environment | Node, in `hello` | Server | May this Node connect |
| client credential | Server operator | Server credential file | CLI, every request | Server | May this caller use the Server |
| node credential | Node | Node credential file, copied to CLI | CLI, every request | Node | One operation on one scope |

Each credential is validated by exactly one party, and that party is the one that
issued it. The Server validates the tunnel token and the client credential; the
Node validates the node credential. Neither side trusts the other's claim about
identity.

A credential is never transmitted. The CLI signs the request with each secret and
sends the signature, so a party that observes the request learns nothing it can
replay.

**No credential carries a permission.** A credential says "you may talk to me". The
policy file says "and you may do this". Keeping those separate is what stops a
stolen client credential from also being a stolen permission.

The node id is not a credential. It is an address: it appears in the URL path and
in every log line, and knowing it grants nothing.

## How a request travels

```
CLI --(client proof + node proof)--> Server
Server verifies the client proof, checks the node id, forwards the node proof
Server --(node proof)--> Node over the open channel
Node verifies the node proof, resolves the scope, checks the policy, does the work
```

The Server never receives the node secret, so it cannot verify the node proof. It
forwards the signature byte for byte and keeps no copy. That is the point: a
compromised Server cannot mint a node proof and cannot recognise one later.

Each proof carries a timestamp and a nonce, and each verifier records the nonces it
has accepted. A captured request therefore cannot be replayed: the Server refuses a
repeated client nonce and the Node refuses a repeated node nonce, in two independent
caches.

The Server serves both surfaces from one listener and one TLS certificate: the
channel at `/channel` for Nodes, the CLI API at `/v1/` for operators. A deployment
that must keep the CLI API unreachable from the internet blocks `/v1/` at the
reverse proxy rather than opening a second port.

Signing does not encrypt. A proof protects the credential and the request, not the
file contents in the response, so TLS is still what keeps a response private.

See `docs/permission-design.md` for the full contract.

## Status

Implemented and verified. The listener, the dialer, the handshake, the CLI and the
three read operations work, and the client and node HMAC boundaries are in place.
The permission model is recorded in `docs/permission-design.md`, the CLI interface
in `docs/API.md`, the configuration surface in `docs/Environment_Variables.md`, and
the test cases in `docs/cases/`.

The first version is read-only: `file.list`, `file.stat` and `file.read`.
`file.write` and `command.exec` are refused at dispatch, so the refusal does not
depend on what a Node advertises.

## Supported platforms

Linux, macOS and Windows. The path fence is implemented with the standard library
`os.Root`, which enforces the boundary on all three, so the platform difference is
a set of path rules rather than a second fence implementation. Windows adds rules
for reserved device names, alternate data streams, trailing dots and
case-insensitive deny-list comparison; they are listed in
`docs/permission-design.md`.

## Skills

Three skills describe how to use the system from each audience's point of view.
Each one is self-contained: a reader who has never seen this repository can follow
it without opening the source.

| Skill | Audience | Answers |
|---|---|---|
| `skills/connector-client/` | The person calling a Node | The `cli` command, its flags, the three read operations, every error code |
| `skills/connector-server-operations/` | The Server operator | Deploy, configure, expose the two surfaces differently, rotate a credential, troubleshoot |
| `skills/connector-node-setup/` | The person running a Node | First-run order, the policy file, scope path rules, start, add and remove a credential |

The Server has two skills rather than one because the two audiences are different
people with different questions. A client never needs to know how to rotate a
secret, and an operator never needs the client's flag syntax.

## Layout

```
topsailai_connector/
├── cmd/
│   ├── connector-server/   # cloud-side entry point
│   └── connector-node/     # personal-computer entry point
├── internal/
│   ├── protocol/           # wire contract shared by both sides
│   ├── security/           # permission vocabulary shared by both sides
│   ├── server/             # cloud-side implementation
│   └── node/               # personal-computer implementation
├── docs/                   # design documents
├── features/               # user-visible behaviour
├── issues/                 # pending, resolved and ignored issues
├── skills/                 # operator and user facing skills
└── tests/                  # integration, bdd and shared fixtures
```

`internal/` is deliberate: the Go compiler refuses an import from outside the
module, so the Node binary cannot accidentally carry server code and the Server
binary cannot carry node code. `internal/protocol` and `internal/security` are
the only packages both sides import, and they must stay free of IO so the two
binaries can never disagree about the contract.

## First run

Three things are generated before the first request: the Server's client
credential, the Node's identity, and the Node's credential. The order matters
because each step needs the previous one's output.

```
1. Create the Server's client credential
   CONNECTOR_NODE_CONFIG_DIR=/etc/connector/server-client \
     connector-node credential add --key-id operator-dawson
     -> operator-dawson.<secret>        copy this; it is printed once

   The credential file is written to /etc/connector/server-client/credentials.yaml.
   The Node binary writes it because the file format has one implementation, and a
   second one in the Server would eventually disagree with it.

2. Start the Server with its tunnel token and that credential file
   CONNECTOR_SERVER_TUNNEL_TOKEN=<secret> \
   CONNECTOR_SERVER_CLIENT_CREDENTIALS_FILE=/etc/connector/server-client/credentials.yaml \
   CONNECTOR_SERVER_LISTEN=:8443 \
     connector-server run

3. Create the Node's identity
   connector-node id
     -> node_7f3a...9c1e      copy this; it is an address, not a secret

4. Write the Node's policy, which is the only place a scope is granted
   cat > /etc/connector/node/policy.yaml <<'YAML'
   version: 1
   scopes:
     project:
       path: /home/me/project
   grants:
     - scope: project
       permissions: [read, list, stat]
   YAML

   A missing policy file is a startup failure, not an implicit allow-all, so the
   Node refuses to start until this file exists.

5. Start the Node with the tunnel token
   CONNECTOR_NODE_TUNNEL_TOKEN=<secret> \
   CONNECTOR_NODE_SERVER_URL=wss://host/channel \
     connector-node run
     -> a new node id was generated by this start
        a new credential was generated by this start

        === connector-node ===
        server        : wss://host/channel
        node id       : node_7f3a...9c1e
        config dir    : /etc/connector/node
        credentials   : /etc/connector/node/credentials.yaml
        policy        : /etc/connector/node/policy.yaml
        scopes        : project
        key id        : bundle-caller
        secret        : <43 characters>
        credential    : bundle-caller.<secret>

        To reach this node from a CLI, set:
          CONNECTOR_CLI_SERVER_URL=https://host
          CONNECTOR_CLI_NODE_ID=node_7f3a...9c1e
          CONNECTOR_CLI_NODE_CREDENTIAL=bundle-caller.<secret>
          CONNECTOR_CLI_CLIENT_CREDENTIAL=<the server's client credential>

   The summary prints on every start, so a restart shows the same values again. The
   secret appears in full only when stdout is a terminal; redirect stdout and it is
   replaced by <secret:N bytes>, so a launcher that logs stdout does not accumulate a
   credential that never expires.

6. Point the CLI at the Node
   CONNECTOR_CLI_SERVER_URL=https://host \
   CONNECTOR_CLI_CLIENT_CREDENTIAL=operator-dawson.<secret> \
   CONNECTOR_CLI_NODE_CREDENTIAL=bundle-caller.<secret> \
   CONNECTOR_CLI_NODE_ID=node_7f3a...9c1e \
     connector-server cli --scope project --path a.txt file.read
```

The Node must run once before anyone can address it, because the Server never
assigns an identifier. The node id is an address, not a credential: knowing it
grants nothing without a node credential and a client credential.

The CLI flags come before the operation name. Go's `flag` package stops parsing at
the first positional argument, so an operation written before a flag turns that
flag into a positional argument and the command fails with a message about
positional arguments rather than about order.

`connector-node regenerate` replaces the node id and prints the new one. It leaves
every credential untouched, so a caller does not have to be reissued a secret
because the Node moved. The live channel drops, because it was authenticated under
the old identity.

`connector-node credential add --key-id <name>` adds a caller, and
`connector-node credential remove --key-id <name>` revokes one. `credential list`
prints the key identifiers and never a secret. The last credential cannot be
removed, because a Node with no credential refuses every caller and the operator
would have no way back in without editing the file by hand.

## Build

```
make build
```

Binaries are written to `bin/`. Test artifacts are written to `.tmp/`, which is
ignored by git.

## Package a Node for someone else

`make package` produces one executable with the configuration compiled in. The
recipient runs it and the Node connects with no configuration file and no
environment variable; the operator can reach the machine with the CLI as soon as
it connects.

```
make package PACKAGE_SERVER_URL=wss://cloud.example.com:8443/channel \
             PACKAGE_SCOPES='project=/home/me/project tool=/opt/tool' \
             PACKAGE_TUNNEL_TOKEN=<tunnel_token> \
             PACKAGE_NODE_KEY_ID=bundle-caller
```

The binary carries the `tunnel_token`, so hand it over the way you would hand over
a password: a leaked binary opens a channel to the Server for every Node on it.

The identity and the credentials are not embedded. Run the binary once with `id` on
the target machine to create the node id, and the first `run` creates one caller
credential. Every `run` then prints the node id, the key id and the secret in its
startup summary, so the operator can read them off the terminal at any time.
`PACKAGE_NODE_KEY_ID` names that credential and defaults to `bundle-caller`; it is
public, so it may appear in a log or a ticket.

`make package-windows` builds the same executable for Windows. `make package-zip`
produces the older zip instead, for a recipient who must edit the scopes themselves
or reload the policy; it carries the node id and one node credential rather than the
Server-wide tunnel token, so a leak exposes one Node. See
`packaging/bundle-README.md` for what the recipient does with a zip.
