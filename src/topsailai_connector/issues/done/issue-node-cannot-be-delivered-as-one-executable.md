# A Node cannot be delivered as one executable, so the recipient must assemble a directory before it runs

## Symptom

The only delivery is a zip bundle. The recipient unpacks it, and the Node then
needs four things before it will connect:

```
connector-node-windows-amd64/
├── connector-node.exe
├── config/
│   ├── identity          # generated at packaging time
│   ├── policy.yaml       # generated by start.ps1 from scopes.txt
│   └── tunnel_token      # written by the packaging step
├── scopes.txt
├── server_url
├── allow_filesystem_root
├── start.ps1
└── start.sh
```

A recipient who copies only `connector-node.exe` gets a startup failure, because
`LoadConfig` requires `CONNECTOR_NODE_SERVER_URL` and a tunnel token, and
`LoadAuthority` requires a policy file. The binary alone is not usable.

The request was for a second packaging mode where the configuration is compiled
into the binary, so the recipient runs one file and the Node is reachable.

## Impact

Handing someone a Node means handing them a directory and a start script. Every
step is a place to make a mistake:

- The start script must be run from the bundle directory, because `scopes.txt` and
  `server_url` are read relative to it.
- On Windows the script must be run from PowerShell, and the execution policy may
  refuse it.
- The tunnel token sits in `config/tunnel_token` as a separate file, so it can be
  copied without the binary or the binary without it.

None of these is a security defect. They are delivery friction, and the friction is
what the request asked to remove.

## Root cause

Configuration has exactly one source: the environment, with a built-in default.
`LoadConfig` reads `CONNECTOR_NODE_SERVER_URL` and `CONNECTOR_NODE_TUNNEL_TOKEN`
through a lookup function, and `LoadAuthority` reads a policy file from disk. There
is no third source, so a binary cannot carry its own configuration.

The policy loader also has no in-memory entry point. `LoadAuthority` takes a path,
opens it, and parses it, so a policy that is already in memory has no way in.

## Design constraint that shaped the fix

The identity pair cannot be embedded, and this is a refusal rather than a
limitation to work around:

- `EnsureIdentity` and `SaveIdentity` persist the pair, `watchIdentity` polls the
  file once per second, and `RegenerateIdentity` rewrites it. An embedded pair has
  no file to watch or rewrite, so `regenerate` would either be unavailable or would
  disagree with the value in memory.
- The Server keeps an in-memory registry `node_id -> connection`. Two machines
  running one binary would share a `node-id`, and the second connection would evict
  the first. An identity that is not unique per machine is not an identity.

So the binary still generates its own pair on first start and prints it once. "Start
it and it works" holds: it connects with no configuration, and the operator runs
`<binary> id` once to learn the pair the CLI must present.

## The security consequence, and why it was escalated

Embedding the `tunnel_token` makes the binary a Server-wide credential. The
residual-risk table already states the consequence: a leaked `tunnel_token` lets
anyone open a channel and impersonate a Node, with every Node in the blast radius.

The live Windows deployment maps one scope to `C:\`, and the binary sits at
`C:\connector-node\...\connector-node.exe`, inside that scope. So `file.read` on the
binary already returns its bytes. Embedding the token without a deny entry would
turn a local secret into a remotely extractable one.

Three options were presented to the human: embed the token and deny the executable;
embed only the Server URL and the policy and leave the token to the environment;
embed nothing and keep the zip. The human chose the first, accepting that the binary
is a credential.

## Resolution

**New package `internal/node/embedded`.** Three linker-injected variables
(`ServerURL`, `TunnelToken`, `PolicyBase64`) plus `Enabled()`, `CarriesSecret()` and
`Policy()`. `CarriesSecret()` is what decides whether the executable joins the deny
list, so a build with only a Server URL and a policy is not refused.

**`LoadConfig` gained a third source.** The environment wins field by field, so an
operator can repoint the same binary without a rebuild. The policy is the deliberate
exception: a build that embedded a policy **refuses** `CONNECTOR_NODE_POLICY_FILE`,
because an embedded policy is a whole document and a file path would silently
replace every scope and every grant.

**`LoadAuthorityBytes` is a new entry point**, not a nil-path special case in
`LoadAuthority`. The two have different failure modes: one reports a missing file,
the other a malformed document. A single function taking an empty path would have to
guess which error the caller meant. Both delegate to a shared `buildAuthority`, so
the scope-opening rules exist once and the fence cannot be configured differently
depending on how the policy arrived.

**The executable joins the deny list** when `embedded.CarriesSecret()` is true.
`os.Executable()` rather than `os.Args[0]`, because the latter is whatever the
launcher typed — relative, a symlink, or a bare PATH name — and the deny list
compares by file identity.

**`packaging/build-package.sh` gained `PACKAGE_EMBED_CONFIG`**, accepting only
`''`/`0` and `1`. The scope list is now written and validated before the binary is
built, because the embedded mode compiles it into the policy. The embedded policy is
generated from the same validated list, with paths written exactly as given and
never resolved on the build host, because the binary runs on another machine.

**`Makefile` gained `package-embedded` and `package-embedded-windows`**, as separate
targets rather than a variable, for the same reason `package-windows` is separate: a
caller who forgot the variable would get a zip and not notice.

## Two defects found by testing the new branch, not by reading it

Both were masked in normal use only because `make package` depends on `build-node`:

1. `$BIN_PATH` was never created in embedded mode. Only the zip branch ran
   `mkdir -p "$STAGE/config" "$BIN_PATH"`, so a build with a non-existent `bin/`
   would fail. Fixed by hoisting `mkdir -p "$BIN_PATH"` above the branch.
2. A host Node binary was required unconditionally, even though embedded mode never
   uses it because it generates no identity. Fixed by making the check conditional
   on `EMBED_CONFIG != 1`.

## What embedding does not protect

`-X` stores the value as plain text in the binary's data section, so
`strings connector-node` recovers it. Verified: the token was found three times in
the built binary. This is stated in the package comment, the design document and the
packaging summary rather than encoded away, because base64, compression and
obfuscation all decode with the same command, and encryption would need a key the
binary must also carry.

The protection that matters is the deny list, which stops a remote caller. A local
user holding the file already has the secret.

## Tests

`internal/node/embedded/embedded_test.go` — 6 tests / 11 subtests. The load-bearing
one is `TestCarriesSecretTracksOnlyTheToken`: a build with a Server URL and a policy
but no token must **not** be refused, because refusing it would break serving the
install directory for no gain.

`internal/node/embedded_config_test.go` — 8 tests, including a paired
positive/negative pair that proves the executable deny entry is conditional:
`TestOpenRefusesTheRunningExecutableWhenTheBinaryCarriesASecret` and
`TestOpenServesTheRunningExecutableWhenTheBinaryCarriesNoSecret`.

A mutation test on `CarriesSecret` was caught by the subtests, and the file was
restored byte-identical.

## Live verification

Two scripts, both passing, both driving a real Server and a real Node built by the
real packaging command.

**`.tmp/embedlive/live.sh`** — the binary starts with `env -i HOME=...`, so no
`CONNECTOR_NODE_*` variable exists at all:

| Check | Result |
|---|---|
| The embedded binary was built | PASS |
| The Node started from the binary alone and connected | PASS |
| The Node reports `policy=embedded` | PASS |
| The Node generated its own identity | PASS |
| `file.read project notes.md` returned the content | PASS |
| A traversal is refused | PASS |

**`.tmp/embedself/live.sh`** — the binary is built **into the scope directory**, so
the scope contains it. This is the deployment shape the Windows host uses.

| Check | Result |
|---|---|
| The embedded binary was built inside the scope | PASS |
| The Node connected | PASS |
| The scope serves a neighbouring file | PASS |
| `file.read` of the binary is refused | PASS |
| The refusal is `denied`, not a different error | PASS |
| The refusal does not echo the tunnel token | PASS |
| `file.stat` of the binary is refused | PASS |
| The listing omits the binary | PASS |
| The listing still shows the neighbouring file | PASS |

The neighbouring-file rows are the control. Without them, a refusal of the binary
could be a refusal of everything, and the test would pass on a broken scope.

## Verified on

Build host, Go 1.25.12. `make check` RC=0, zero `FAIL`, total coverage 89.8%
(`internal/node` 91.9%, `internal/node/embedded` 100.0%, `internal/node/policy`
95.4%). Windows cross-compile for amd64, arm64 and 386, and the Windows test
binaries, all compiled.

An embedded Windows binary has **not** been executed on a Windows host. The
cross-build compiles; the live runs above are Linux only.
